# 后续规划

## 1. FinMate Backend 增强

当前 iOS/Web 已统一使用独立 FinMate Backend。后续重点是在后端侧稳定接入基金和美股上游，并继续保持 `/v1/*` API 对客户端稳定。

### 1.1 待完成

- 明确可长期运行的上游接口。
- 标准化 `/v1/stocks/quote` 字段映射。
- 标准化 `/v1/stocks/search` 字段映射。
- 标准化 `/v1/stocks/kline` 字段映射。
- 增加后端侧缓存和限流。
- 持续完善 `/health` 和 `/openapi.json` 部署检查。
- 统一错误码：鉴权失败、上游超时、限流、无数据、字段异常。

### 1.2 后端缓存建议

| 市场状态 | TTL |
|---|---:|
| 交易中 | 3-10 秒 |
| 盘前/盘后 | 10-30 秒 |
| 休市 | 5-30 分钟 |
| 上游失败 | 返回最近缓存并标记 stale |

## 2. 支付宝基金截图 OCR 导入

目标：用户上传支付宝基金持仓截图，FinMate Backend 进行 OCR 和结构化解析，App 展示确认页后批量添加/更新基金。

### 2.1 推荐流程

```text
基金 Banner 点击 +
  -> 选择“手动添加基金”或“从支付宝截图导入”
  -> 选择截图
  -> 上传 FinMate Backend
  -> OCR + 基金匹配 + 数据推导
  -> App 确认页
  -> 用户确认/修正/忽略
  -> 批量写入本地持仓
```

### 2.2 关键限制

支付宝截图不一定包含成本价和份额。常见字段可能只有基金名称、持有金额、持有收益、收益率。因此第一版不能直接无确认导入。

可推导公式：

```text
costAmount = holdValue - profit
shares = holdValue / currentPrice
costPrice = costAmount / shares
```

这类结果必须标记为推导值，并允许用户修正。

```http

Content-Type: multipart/form-data
Authorization: Bearer <BRIDGE_ACCESS_TOKEN>
```

## 3. 性能优化方向

- 进一步拆分过大的 SwiftUI View，降低 body 类型推导压力。
- K 线和业绩走势按 symbol/code + range 做更明确的缓存 TTL。
- 输入页减少不必要的布局层级，保证键盘聚焦更快。
- FinMate Backend 增加批量报价接口，减少美股多持仓时的并发请求数量。
- 真机验证首页底部安全区、横滑误触、长列表滚动性能。

## 4. 视觉优化方向

只做轻量优化：

- 加强主次层级。
- 统一圆角和间距。
- 降低明显边框。
- 统一基金/美股 Banner 组件位置。
- 优化图表加载态和失败重试。

不要再回到液态玻璃方向，也不要调整已认可的列表内容结构。
